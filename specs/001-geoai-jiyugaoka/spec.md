# 機能仕様書: 自由が丘 ArcGIS GIS根拠付きコーヒー推薦 PoC

**機能ブランチ**: `001-geoai-jiyugaoka`  
**作成日**: 2026-04-03  
**状態**: Draft  
**入力**: ユーザー要望: 「GeoAI の PoC を作りたいが、ArcGIS Personal Use では GeoAI/API が使えない可能性がある。対象は東京・自由が丘。一般的な LLM が何となく答える形は避け、ArcGIS と GIS 的な根拠でコーヒーショップまたはコーヒー豆店を選定したい。ベスト 3 提示またはニーズの絞り込みができるようにしたい。」

## ユーザーシナリオとテスト

### ユーザーストーリー1 - 自然言語からの GIS 根拠付き推薦 (優先度: P1)

レビュー担当者が「静かで豆もちゃんとしている店に行きたい」のような自由記述の日本語入力を行うと、自由が丘にあるコーヒーショップまたはコーヒー豆店について、GIS 的な根拠を持つ推薦結果が返る。

**この優先度である理由**: これが PoC の中核的な主張だからです。自然言語入力を、ArcGIS の使い方が見える形で、説得力のある GIS 根拠付き推薦へ変換できなければ、UI や補助機能が良くてもデモとして成立しません。

**独立テスト**: 多様な日本語入力を与えたときに、絞り込み質問に依存せず、自由が丘内の候補が最大 3 件まで返り、それぞれに GIS ベースの説明が付いていることを確認すれば単独で検証できます。

**受け入れシナリオ**:

1. **前提**: アプリが自由が丘をアクティブな検索エリアとして表示している  
   **操作**: ユーザーがコーヒー店舗に関する自然言語の希望を入力する  
   **期待結果**: 承認されたエリア内にあるコーヒーショップまたはコーヒー豆店に限定した推薦候補が、最大 3 件返る
2. **前提**: 推薦結果が返っている  
   **操作**: 結果カードを表示する  
   **期待結果**: 各推薦には、ArcGIS 管理データまたは明示的な GIS ルールから導かれた、空間・カテゴリ・範囲に関する説明が含まれ、一般的な LLM 風の曖昧な要約にはならない
3. **前提**: 2 人のユーザーが似た意図を別の日本語表現で入力する  
   **操作**: 両方の入力を処理する  
   **期待結果**: 言い回しが違っても、結果ゼロや無関係な候補に崩れずに処理できる

---

### ユーザーストーリー2 - GIS レビュー担当者が選定理由を確認できる (優先度: P2)

GIS のレビュー担当者が推薦結果を見て、どの ArcGIS 可視要素、制約、データセット、ランキング要因によって候補が選ばれたのかを理解できる。

**この優先度である理由**: 想定閲覧者は、本当に GIS 中心の仕組みかどうかを見ます。説明可能性と追跡可能性は、デモの信頼性に直結します。

**独立テスト**: どの推薦結果セットでも、各候補が上位に入った理由を UI から GIS の観点で説明できるかを確認すれば単独で検証できます。

**受け入れシナリオ**:

1. **前提**: 推薦結果が表示されている  
   **操作**: レビュー担当者が候補の説明を開く  
   **期待結果**: 空間範囲、カテゴリ絞り込み、ランキング根拠、データ由来、ArcGIS ベースの可視化文脈など、GIS に関係する説明が表示される
2. **前提**: ある候補が推薦されている  
   **操作**: レビュー担当者が「なぜ入ったのか」を確認する  
   **期待結果**: ArcGIS に基づくロジック、明示的な GIS ルール、または地理制約に基づく説明が返り、「AI が良いと判断した」のような曖昧な理由だけでは終わらない

---

### ユーザーストーリー3 - 曖昧なニーズに対する絞り込み (優先度: P3)

入力が広すぎたり曖昧だったりする場合、最終的な推薦を確定する前に、追加質問または解釈しやすい絞り込み選択肢を提示できる。

**この優先度である理由**: 使いやすさは向上しますが、まず証明すべきなのは、第一段階の GIS 根拠付き推薦ループが成立することです。

**独立テスト**: たとえば「いい感じの店」のような曖昧な入力を与えたときに、最終結果を出す前に絞り込み質問や構造化された選択肢を提示できるかで検証できます。

**受け入れシナリオ**:

1. **前提**: ユーザーが曖昧な要望を入力する  
   **操作**: システムが要件不足と判断する  
   **期待結果**: 自由が丘での店舗選びに関係する絞り込み質問や選択肢を 1 つ以上提示する
2. **前提**: ユーザーが追加質問に回答する  
   **操作**: 推薦を再計算する  
   **期待結果**: 承認済みの地理範囲や店舗カテゴリから外れず、結果がより具体的になる

### エッジケース

- 渋谷や清澄白河など、自由が丘以外を求める入力をした場合はどうなるか
- バー、ベーカリー、レストランなど、非対応カテゴリを混ぜた場合はどうなるか
- キュレーション済みデータセットまたは ArcGIS 上で見える候補群が少なすぎる場合、どう応答するか
- 「いい感じ」「失敗したくない」など、非常に曖昧な入力のときどう振る舞うか
- ArcGIS 依存の地図機能が一時的に使えない場合どうするか
- コーヒーを飲みたい意図と豆を買いたい意図が両方ある場合どうするか

## 要件

### 機能要件

- **FR-001**: MVP では、推薦処理全体を東京・自由が丘に限定しなければならない
- **FR-002**: MVP では、候補カテゴリをコーヒーショップとコーヒー豆店に限定しなければならない
- **FR-003**: ユーザーは、雰囲気、目的、味、店舗特性を自由な日本語で入力できなければならない
- **FR-004**: 日本語の言い回しの違いに耐え、定型文選択を必須にしてはならない
- **FR-005**: 推薦生成とランキングの主軸は、ArcGIS 上で見えるデータ、地図文脈、または明示的な GIS ルールでなければならない
- **FR-006**: 一般的な LLM を推薦判断の主役にしてはならない。LLM を使う場合でも、任意の言語解釈補助にとどめ、非決定的な補助出力として扱わなければならない
- **FR-007**: 有効な入力に対して、条件を満たす候補がある場合は最大 3 件まで返さなければならない
- **FR-008**: 各推薦候補について、GIS のレビュー担当者に説明できる GIS 関連の理由を表示しなければならない
- **FR-009**: 選ばれた候補は、MVP で定めた地理範囲に合わせた地図上に表示しなければならない
- **FR-010**: 推薦がコーヒーショップなのか、コーヒー豆店なのか、両方なのかを明示しなければならない
- **FR-011**: 曖昧な入力に対しては、妥当な第一段階の Top 3 を返すか、追加の絞り込み質問を出してから確定しなければならない
- **FR-012**: ArcGIS 依存の可視化が使えない場合や候補が不足する場合でも、破綻せず、その制約をユーザーに明確に伝えなければならない
- **FR-013**: デモ時に、ArcGIS のどの機能、サービス、可視化、GIS ルール、またはキュレーション済みデータセットが推薦に寄与しているか識別できなければならない
- **FR-014**: 根拠のない自信、作り話の説明、GIS 根拠にたどれない一般的な「AI っぽい」回答を出してはならない
- **FR-015**: ArcGIS Personal Use の制約下でも実装可能でなければならず、GeoAI や推薦 API が使えない可能性も考慮しなければならない
- **FR-016**: ArcGIS による地図・可視化の挙動と、ローカル計算によるランキングの挙動が併存する場合、それぞれを明確に区別して示さなければならない

### 主要エンティティ

- **User Intent**: 希望する雰囲気、利用目的、購入目的、店舗特性を表す自由記述の日本語入力
- **Search Area**: 自由が丘を表す MVP の境界付き地理範囲。結果を範囲内に留めるためのルールも含む
- **Venue Candidate**: 推薦対象となるコーヒーショップまたはコーヒー豆店。カテゴリ、位置、GIS 属性、由来情報、説明項目を含む
- **Recommendation Result**: 地図表示位置、順位、GIS 根拠付き説明を含むランキング済み出力
- **Refinement Prompt**: 初回入力が曖昧なときに、より確度の高い推薦に絞るための追加質問または選択肢

## 成功条件

### 計測可能な成果

- **SC-001**: デモで表示される推薦の 100% が、自由が丘内かつ許可されたカテゴリ内に収まっている
- **SC-002**: 代表的な日本語入力セットに対して、80% 以上の試行で少なくとも 1 件の妥当な候補を返せる
- **SC-003**: 表示される全推薦について、GIS レビュー担当者が ArcGIS 上で見えるロジック、明示的な GIS ルール、または地理制約に説明をたどれる
- **SC-004**: 内部レビュー時に、「一般的な LLM が最終判断した」と主張しなくても推薦ワークフローを説明できる
- **SC-005**: 曖昧な入力に対して、1 ステップ以内で妥当な Top 3 を返すか、追加確認を促せる

## 前提

- 主なデモ観客は GIS に詳しいレビュー担当者であり、ArcGIS の使い方と GIS 的な推論が本当に中心かを確認する
- ArcGIS Personal Use ライセンスは利用可能だが、GeoAI や推薦 API は利用不可または不向きである可能性がある
- 標準のデモ画面は 1920x1080 を前提とする
- 初期 MVP ではスマホ向けレスポンシブ対応は低優先とし、まずはデスクトップで安定して見やすければよい
- 自由が丘向けの境界付きキュレーションデータセットを使ってもよいが、推薦処理全体は GIS 的根拠と説明可能性を保たなければならない
- 追加の絞り込みは望ましいが、まずは第一段階の GIS 根拠付き推薦体験を成立させることが優先
